# @good-ground-collective/agentic-communication-standards

Zod schemas for the messages that pass between Dash's components: Mission Control, the web app, the hooks and the bench daemon. Each component builds against this package, so nobody keeps a hand-synced copy of a message shape.

## Install

The package is published to GitHub Packages. Map the scope and supply a token with `read:packages`:

```sh
echo '@good-ground-collective:registry=https://npm.pkg.github.com' >> .npmrc
echo '//npm.pkg.github.com/:_authToken=${NODE_AUTH_TOKEN}' >> ~/.npmrc
pnpm add @good-ground-collective/agentic-communication-standards zod
```

## The envelope

Every message has the same outer fields:

| Field           | What it holds                                                |
| --------------- | ------------------------------------------------------------ |
| `schemaVersion` | `"<major>.<minor>"`, versioned per message kind              |
| `kind`          | A dotted message name, such as `example.ping`                |
| `id`            | A UUID, unique per message, so receivers can drop duplicates |
| `emittedAt`     | An ISO 8601 UTC timestamp, such as `2026-11-27T09:30:00Z`    |
| `payload`       | The message-specific body                                    |

Sender identity, sessions and sequence numbers are not part of the envelope yet.

```ts
import { examplePing } from '@good-ground-collective/agentic-communication-standards';

const ping = examplePing.schema.parse(JSON.parse(body));
```

## JSON Schema

Consumers that don't run TypeScript can read the same schemas as JSON Schema (draft 2020-12). The package ships one file per message kind and major version:

```js
import { createRequire } from 'node:module';

const require = createRequire(import.meta.url);
const path =
  require.resolve('@good-ground-collective/agentic-communication-standards/schemas/example.ping.v1.json');
```

The files are generated from the Zod schemas and committed under `schemas/`. They describe what a reader accepts, so they allow unknown fields. CI fails when they are stale.

## Go

`go/` is a Go module, `github.com/Good-Ground-Collective/dash/packages/standards/go`, with one generated file per JSON Schema file, such as `go/example_ping_v1.go` for `schemas/example.ping.v1.json`. Its `standards` package has a struct per message, such as `ExamplePingV1`, whose `UnmarshalJSON` checks required fields, lengths, patterns and constants. Like the Zod schemas, the structs ignore fields they don't know.

```go
var ping standards.ExamplePingV1
if err := json.Unmarshal(body, &ping); err != nil {
	return err
}
```

The structs are generated by [go-jsonschema](https://github.com/atombender/go-jsonschema) v0.24.1, run with `go run`, so it needs Go but nothing else installed. `scripts/generate-go.sh` holds the exact command. The `standards-go` CI job reruns it and fails when the committed files differ, then runs `go vet` and `go test`. Together with the JSON Schema check, a stale file anywhere along Zod → JSON Schema → Go fails CI.

One difference to know about: go-jsonschema reads `emittedAt` as a `time.Time`, which accepts any RFC 3339 offset, while the Zod schema accepts only UTC (`Z`). Writers must set `EmittedAt` with `.UTC()`, or Zod readers reject the message.

### Shared fixtures

`fixtures/<kind>.v<major>/valid/` and `fixtures/<kind>.v<major>/invalid/` hold JSON messages that the Zod tests, the JSON Schema and the Go test (`go/fixtures_test.go`) must all accept or all reject. That is what shows the two sides agree, rather than only that both generators ran. The Go test also re-encodes each valid message and checks it kept every known field's value. Add fixtures for every new message, and a case to `decoders` in `go/fixtures_test.go`; the Go test fails for a schema without both.

### Go module versions

Inside this repository, a Go consumer such as the bench daemon uses the module through a `replace` directive or a `go.work` file, so it needs no tags. If a consumer outside the repository appears, the module needs tags of the form `packages/standards/go/vX.Y.Z`, because it lives in a subfolder, and a major version of 2 or higher needs a `/v2` suffix on the module path. The publishing pipeline will add those tags when that happens; nothing creates them yet.

## Agent heartbeats

`agent.heartbeat` (`agentHeartbeat`) is what a harness hook sends each time an agent's state changes. Mission Control keeps the latest one per session, raises the ones that need you and notices the ones that go quiet. Token and cost figures are not part of it; they come from OpenTelemetry.

| Field       | Required | What it holds                                                                                                      |
| ----------- | -------- | ------------------------------------------------------------------------------------------------------------------ |
| `sessionId` | yes      | The harness session. A subagent carries its parent's session ID                                                    |
| `seq`       | yes      | A non-negative integer that increases within the session (see below)                                               |
| `harness`   | yes      | An open enum: `claude-code` (in `knownHarnesses`) or any lowercase dotted or dashed name, up to 64 characters      |
| `status`    | yes      | Exactly one of the statuses below                                                                                  |
| `agentId`   | no       | Set only for a subagent, so it rolls up under the parent session                                                   |
| `agent`     | no       | `{ type?, model? }`: the agent type, such as a subagent name, and the model it runs on                             |
| `summary`   | no       | The last assistant message, trimmed                                                                                |
| `question`  | no       | `{ text, options?: [{ label, description? }] }`, copied verbatim from the harness. Set when `status` is `question` |
| `error`     | no       | `{ kind, message }`. Set when `status` is `error`                                                                  |
| `workspace` | no       | `{ directory?, repository?, branch? }`: where the agent is working                                                 |
| `machine`   | no       | The hostname the agent runs on                                                                                     |
| `taskId`    | no       | The task the session serves. A session serves one task; a task can span sessions                                   |

The envelope's `emittedAt` is the heartbeat's timestamp. Ticket and pull request links aren't in v1; the board joins those from GitHub.

### Statuses

The statuses don't overlap, so a hook picks exactly one. The A2A column is the nearest [A2A task state](https://a2a-protocol.org/latest/specification/), for anything that bridges heartbeats to A2A.

| Status     | Meaning                                                                                                                      | When a hook emits it                                                                  | A2A              |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- | ---------------- |
| `working`  | The agent is making progress on its own                                                                                      | A prompt is submitted, or a tool call starts or finishes                              | `working`        |
| `waiting`  | The agent is waiting on something external that isn't you, such as CI, a deploy or a subprocess, and will continue by itself | A tool call is waiting on a background process or an outside system                   | `working`        |
| `question` | The agent needs input from you. This raises a Needs you item and a push notification                                         | An AskUserQuestion `PreToolUse`, a permission prompt or an idle prompt `Notification` | `input-required` |
| `blocked`  | The agent can't proceed without outside action, and isn't asking a specific question                                         | The agent stops and reports that something outside it has to change first             | `input-required` |
| `complete` | The turn or task finished successfully                                                                                       | `Stop`, or `SubagentStop` for a subagent                                              | `completed`      |
| `failed`   | The agent finished without achieving the task                                                                                | `Stop` or `SubagentStop` when the harness can tell the task wasn't done               | `failed`         |
| `error`    | The harness or the hook hit an error, such as a crash or an API failure. Carries `error`                                     | A model API error, a harness crash or a hook that fails                               | `failed`         |

A2A's `canceled` has no heartbeat status: a session someone interrupts sends its next heartbeat when it resumes, and one that never resumes goes stale and then lost.

### Length limits

| Field              | Limit                                                 |
| ------------------ | ----------------------------------------------------- |
| `summary`          | 500 characters                                        |
| `question.text`    | 2,000 characters                                      |
| `question.options` | 10 options; `label` 200 characters, `description` 500 |
| `error.message`    | 2,000 characters                                      |

Limits count UTF-16 code units, which is what Zod's `.max()` measures. JSON Schema and the Go structs count code points, which is never more, so text within a limit passes all three. A writer in any language must trim by UTF-16 length; trimming by characters can leave emoji-heavy text over the limit for TypeScript readers. Hooks trim to fit, keeping the start and ending with `…`. The schema rejects anything longer, so a writer that forgets to trim fails loudly instead of storing a very long message.

### The `seq` rule

`seq` keeps increasing for the whole life of a `sessionId`, including after `claude --resume`, which keeps the session ID. A hook persists the last `seq` per session and continues from there, so a resumed session never reuses a number. Mission Control drops a heartbeat whose `(sessionId, seq)` it has already stored. Subagents share their parent's `sessionId`, so the parent and its subagents draw from one `seq` counter. Hooks run as separate processes, and a single agent's parallel tool calls fire hooks at the same moment too, so a writer must increment the counter atomically, for example under a lock file; a plain read-then-write can hand two heartbeats the same `seq`, and the second is dropped as a duplicate. The schema checks only that `seq` is a non-negative integer.

## Adding a message

1. Create `src/messages/<area>.ts` and construct a `MessageDefinition` with the kind, the starting version (`1.0`) and a `z.object` payload. `src/messages/example.ts` is the model.
2. Add the definition to `messageRegistry` in `src/registry.ts`. Generators read the registry, so a message missing from it is missing from the generated schemas.
3. Export it from `src/index.ts`.
4. Run `pnpm --filter @good-ground-collective/agentic-communication-standards generate`, then `packages/standards/scripts/generate-go.sh`, and commit the new files in `schemas/` and `go/`. Do the same after any schema change.
5. Add valid and invalid messages under `fixtures/<kind>.v<major>/`, and the new type to `decoders` in `go/fixtures_test.go`.

## Versioning rules

### Minor and major bumps

A minor bump (`1.0` → `1.1`) is any change an older reader can still read:

- adding an optional field
- adding a value to an enum marked open

A major bump (`1.4` → `2.0`) is any change that can break an existing reader or writer:

- removing or renaming a field
- making a field required
- narrowing a type
- adding a value to a closed enum

### How readers behave

- Readers ignore fields they don't know. Wire schemas use `z.object`, which strips unknown keys, never `z.strictObject`.
- Readers reject a message whose major version they don't know, and accept any minor version of a major they do. `MessageDefinition` builds this into `schemaVersion`: a `1.0` definition accepts `1.0` and `1.7` and rejects `2.0`.

### Keeping schemas portable

Wire schemas avoid transforms and refinements that JSON Schema can't express, so the generated JSON Schema says the same thing as the Zod schema. Prefer `.min()`, `.max()`, `.regex()`, `z.enum` and `z.literal` over `.transform()`, `.refine()` and `.superRefine()`.

### The package version

The package's own major version moves only when a message's major version moves. New messages and minor message bumps are minor package releases.

Releases are cut from `main` by CI, tagged `standards-vX.Y.Z`, separately from the repository's `vX.Y.Z`. Only commits that touch `packages/standards/` count, so write them as `feat(standards): …`, `fix(standards): …`, or with a `!` for a major. The root README's Release pipeline section has the details.

`zod` is a peer dependency. The exported schemas are Zod objects, and consumers extend and compose them with their own Zod, so they must share one copy. Install `zod@^4` alongside the package.

## Telemetry attributes

Telemetry attribute names follow the [OpenTelemetry GenAI semantic conventions](https://github.com/open-telemetry/semantic-conventions/blob/v1.45.0/docs/registry/attributes/gen-ai.md), so the same attributes can go out over OTLP later without renaming anything. `genAiAttributes` holds the names, `telemetryAttributesSchema` is a flat, all-optional attribute set that messages embed, and `genAiSemconvVersion` is the pinned release, `1.45.0`.

```ts
import {
  genAiAttributes,
  telemetryAttributesSchema,
} from '@good-ground-collective/agentic-communication-standards';

const attributes = telemetryAttributesSchema.parse({
  [genAiAttributes.requestModel]: 'claude-opus-4-1',
  [genAiAttributes.usageInputTokens]: 1200,
});
```

### The `dash.*` rule

Anything the semantic conventions don't cover goes under `dash.*`, in `dashAttributes`. Never put a field of our own under `gen_ai.*`: a later semconv release could claim the name with a different meaning.

### The pinned release

The GenAI conventions are still in development, and names change between releases. `src/telemetry/semconv-v1.45.0.json` lists every `gen_ai.*` attribute in the pinned release, and a test fails if a constant names one that isn't on the list. Deprecated names, such as `gen_ai.system` and `gen_ai.usage.prompt_tokens`, are left off it. Moving to a new release is a deliberate change with its own pull request: replace the list, bump `genAiSemconvVersion`, and rename any constants the release renamed.

In 1.45.0 the core registry marks the GenAI attributes as moved to the [semantic-conventions-genai](https://github.com/open-telemetry/semantic-conventions-genai) repository, where they are still in development. Its first release, 0.1.0, renames `gen_ai.usage.cache_creation.input_tokens` to `gen_ai.usage.cache_write.input_tokens`.

### Mapping

| Attribute                                  | Stability in semantic-conventions-genai | What it means for Dash                                        |
| ------------------------------------------ | --------------------------------------- | ------------------------------------------------------------- |
| `gen_ai.provider.name`                     | Development                             | The model provider, such as `anthropic` or `openai`           |
| `gen_ai.request.model`                     | Development                             | The model an agent asked for                                  |
| `gen_ai.response.model`                    | Development                             | The model that answered, which can differ from the request    |
| `gen_ai.operation.name`                    | Development                             | What the agent was doing, such as `chat` or `execute_tool`    |
| `gen_ai.conversation.id`                   | Development                             | The harness session, such as a Claude Code session ID         |
| `gen_ai.agent.id`                          | Development                             | The agent's unique ID                                         |
| `gen_ai.agent.name`                        | Development                             | The agent's human-readable name                               |
| `gen_ai.tool.name`                         | Development                             | The tool an agent called                                      |
| `gen_ai.usage.input_tokens`                | Development                             | Input tokens, including cached ones                           |
| `gen_ai.usage.output_tokens`               | Development                             | Output tokens                                                 |
| `gen_ai.usage.cache_read.input_tokens`     | Development                             | Input tokens served from the provider's prompt cache          |
| `gen_ai.usage.cache_creation.input_tokens` | Development                             | Input tokens written to the provider's prompt cache           |
| `dash.usage.cost_usd`                      | Dash                                    | What the usage cost, in US dollars; semconv has no cost field |

What gets reported, and when, belongs to the heartbeat and telemetry discussions.

## Bench messages

The bench daemon and Mission Control exchange these messages, all at `1.0`. The daemon is written in Go and builds against the generated structs, so both sides share one definition.

| Kind                   | Export               | What it holds                                                                                                                                 |
| ---------------------- | -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `bench.info`           | `benchInfo`          | Hostname, OS and version, architecture, CPU model and cores, total memory, daemon version                                                     |
| `bench.metrics`        | `benchMetrics`       | One sample with its `sampledAt` time: CPU, memory, disk per volume, network bytes since the previous sample                                   |
| `bench.processes`      | `benchProcesses`     | Per watched name: running, instance count, combined CPU and memory. No process ids or command lines                                           |
| `bench.harnesses`      | `benchHarnesses`     | Each harness the daemon found, by allowlist id, with its installed version                                                                    |
| `bench.config`         | `benchConfig`        | What the daemon pulls from Dash: the watch list and the sampling interval                                                                     |
| `bench.command`        | `benchCommand`       | A request to update one harness, naming it by allowlist id. Unknown fields are ignored, but `command`, `commandLine` and `args` fail to parse |
| `bench.command-result` | `benchCommandResult` | The outcome: exit status, a trimmed tail of the output, the version afterwards                                                                |

`bench.command` follows the versioning rules: readers ignore fields they don't know. The exception is `command`, `commandLine` and `args`, which Zod and the JSON Schema reject by name, the JSON Schema through a `propertyNames` exclusion. The generated Go struct has only `commandId` and `harnessId` and ignores unknown fields, so a Go reader has no field that can hold a command line. The forbidden names live in one constant, `forbiddenCommandKeys`.

A daemon that backfills after being offline sends one `bench.metrics` message per sample, each with its own `sampledAt`; there is no batch shape.
